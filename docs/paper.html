Refresh or Wait?
A Leakage-Aware Look at Content Refresh Prioritization

Ahmed Hayder

Abstract

Content teams cannot manually review every page every month, so the question this work asks is: which pages deserve a refresh review first? I built a rule-based baseline from staleness and historical traffic volume, discovered — and corrected — a label-leakage flaw in that baseline, then trained Logistic Regression and Random Forest models on features knowable before the outcome month. After correction, the baseline scored below random (0.020 vs. a 0.156 base rate at precision@50), while Random Forest reached 0.700. The finding is directional and decision-support only: simple recency-and-volume heuristics are not just weak here, they are mildly misleading, and a learned model built on honestly-split, leakage-checked features offers a materially better starting point for prioritization.

Introduction

FlyRank's content teams manage large libraries of SEO content across many clients. Deciding which pages to refresh, protect, or leave alone is currently guided by hand-written rules — thresholds on individual signals like how stale a page is or how much traffic it once had. This work supports one concrete decision: given a fixed review capacity each month, which pages should be reviewed first? The goal isn't to prove a causal effect of refreshing content, but to produce a better-than-heuristic ranking that a content team could act on.

Data

Data comes from the FlyRank ML Internship warehouse release (Hugging Face, gated dataset). Two tables were used: dim_content (static content metadata — creation/update dates, content type, word count, category count, competition, backlinks) and fact_content_daily_performance, aggregated to page-month grain for February 2026 and March 2026 — a mid-panel window chosen deliberately over the final month, which the internship treats as a sealed test month.

Excluded, on purpose:

  • Any client- or content-identifying information beyond the provided pseudonymous hash IDs
  • FlyRank's existing product health-score or refresh flags — using them as model inputs would mean learning to reproduce an existing decision, not making a new one
  • The final panel month (sealed test, never touched for label or feature logic)
  • March-month traffic columns as features — March defines the label, so using it as an input would be leakage (see Methodology)

Methodology

Label

is_declining — an observed proxy I define directly, not a FlyRank-provided outcome: 1 if a page's March impressions are lower than its February impressions, else 0. Base rate in the test set: 15.6%.

Features (February and earlier only)

days_since_update, impressions_feb, avg_position_feb, ctr_feb, plus static dim_content fields (word_count, category_count, competition, backlinks). No March-month traffic figures are used as inputs, since March is where the label comes from.

Baseline — and a correction worth naming

The first version of the rule scored pages as stale × visible × declining × impressions_feb — and scored suspiciously close to perfect. The problem: it multiplied by the very quantity (declining, from March data) that the evaluation label is built from, so it wasn't ranking, it was echoing its own answer. The corrected baseline drops that term: stale × visible × impressions_feb, evaluated against is_declining purely as ground truth, never as an input.

Validation design

Grouped split by client (GroupShuffleSplit, 80/20, random_state=42) — 40 clients in train, 10 in test, confirmed zero client overlap. A client's pages share systemic factors (industry, overall SEO health), so a random row-level split would leak client identity into the test set.

Results

Base rate (random)0.156

Feature importance

Random Forest: impressions_feb (46.3%), avg_position_feb (33.7%), days_since_update (9.4%). No single feature dominates near-100%, and Logistic Regression's coefficients agree on the same ordering — a reassuring cross-check against leakage, and a plausible story: past traffic and rank position carry most of the signal about whether a page is currently declining.

Error analysis

Manual review of misclassified pages showed the model mainly fails on borderline cases — pages whose current-month snapshot doesn't clearly signal direction of change, because none of the features capture momentum directly. A page with moderate traffic and position can look stable in a single-month snapshot while already mid-decline.

Limitations & Honest Framing

  • Built on a single month-pair (Feb→Mar 2026), not multiple periods — stability across other month-pairs is untested.
  • No momentum features (e.g., percentage change vs. two months prior) were included yet; error analysis suggests these would help most.
  • All results are observed and directional, describing association within this data slice — not a causal claim about what refreshing content does, and not a claim about Google's ranking algorithm.
  • This is decision-support, not an autonomous action system: outputs are meant to prioritize human review, not replace it.

Ranked Recommendations

For each review cycle, rank pages by the Random Forest's predicted probability of decline and route the top of that list to review_for_refresh. Two concrete guardrails from this work:

  • Do not use staleness and past volume alone as a review trigger — this study's corrected baseline shows that heuristic performing worse than random.
  • Treat borderline-probability pages as lower-confidence — the error analysis shows these are exactly where the current feature set is weakest; a temporal-change feature is the highest-value next addition before trusting scores near the decision boundary.
